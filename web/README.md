# Personality-to-Place: web app

The browser version of the test. Product overview, how to take it, how scoring and grading work: see the [main README](../README.md). This page is for people working on the code.

## Commands

```bash
npm install
npm run dev          # http://localhost:3000
npm run build        # production build
npm start            # serve the production build

npm test             # 114 tests: scoring parity with Python, grading, saved progress
npm run mutation     # mutation test of lib/scoring.ts and lib/grading.ts (about 2 minutes)
npm run canary       # drift, known answers, planted faults; add a URL to smoke-test a live site
npm run e2e          # Playwright, real browser, against http://localhost:3000; add a URL for a deployed site
npm run data         # regenerate data and fixtures from ../src and ../build (needs python3)
```

## Map

| Piece | Where | Notes |
|---|---|---|
| Questions, keys, locations | `data/test-data.json` | Generated by `../build/export_web.py`. Never edit by hand. |
| Scoring, Steps 1 to 9 | `lib/scoring.ts` | A port of `../build/scoring.py` and `../build/score_answers.py`. Pure function, under 1 ms. |
| Grades and their reasons | `lib/grading.ts` | Clarity bands, scale levels, fit letters, and the explanation for each. |
| Saved progress | `lib/store.ts` | zustand + localStorage, written on every answer. Backup file for moving between devices. |
| Screens | `components/` | `HomeView`, `TestRunner`, `PartsPanel`, `ResultsView`, `BackupControls`. |
| Tests | `tests/` | `scoring.test.ts`, `grading.test.ts`, `store.test.ts`, `mutation.mjs`, `canary.mjs`, `e2e.mjs`, `fixtures.json` (generated). |

## The rule that keeps scoring honest

`../src` and `../build/scoring.py` are the source of truth. `lib/scoring.ts` is a second implementation that must agree with Python exactly, with no rounding tolerance. So after changing a question or a rule:

```bash
npm run data         # rewrites data/test-data.json and tests/fixtures.json
npm test             # must stay green
npm run mutation     # must end with "MUTATION: PASS"
npm run canary       # must end with "CANARIES: PASS"
```

What each layer catches:

- **Parity tests** catch a scorer that disagrees with Python on 67 answer sheets, 250 random profiles, 1,500 synthetic places, 421 dealbreaker cases, and the three worked examples.
- **Mutation testing** catches tests that have gone blind. It changes the scoring and grading code one small step at a time (over 500 changes) and requires the tests to notice every one. The few changes that cannot alter any result are listed in `tests/mutation.mjs` with the reason, and a stale entry fails the run.
- **Canaries** catch broken guard rails: shipped data that no longer matches the sources, and a test suite that would pass on corrupted data.
- **End to end** catches a broken product: it starts, answers, skips, pauses, reloads, resumes in a new tab, backs up, restores, finishes, scores, and reads the grades in a real browser.

## Deploy

```bash
vercel --prod        # from this folder
```

If you connect the GitHub repository to Vercel instead, set the project's Root Directory to `web`.

## Sharp edges

- Next.js 16 has breaking changes from earlier versions. Read `AGENTS.md` and the guides in `node_modules/next/dist/docs/` before changing framework code.
- Storage never throws. `lib/store.ts` wraps localStorage so a damaged save starts clean (the damaged text is kept under `personality-to-place:v1:damaged`), a hand-edited save is cleaned by `sanitize`, and a browser that blocks storage shows a warning instead of crashing.
- The store uses `skipHydration`. Saved progress loads after mount (`useHydrated`), so the first client render matches the server's. Reading the store during render before `useHydrated()` is true shows empty progress.
- Question numbers are the storage key for answers. Reordering questions in `../src` would silently misalign saved answers; add questions at the end of a part only if you also bump the storage key in `lib/store.ts`.
